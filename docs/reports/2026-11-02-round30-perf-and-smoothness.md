# 第 30 轮：性能与操作手感打磨（版本 2026.11.02.12）

用户诉求：「性能 用户操作丝滑体验感细节打磨下」。

## 一、先量，再改

隔离实例（8894，复制 `canvas.db`，项目 `gk6woLnGjh998UeNwvhqYG`：127 节点 / 441 连线，
视口内 22 节点 / 54 连线）+ Chrome CPU profile + trace。

### 改前基线

| 场景 | p50 | p90 | p99 | 最长帧 | >32ms 的帧 |
|---|---|---|---|---|---|
| 静止 | 16.7 | 16.8 | 16.8 | 16.9 | 0 |
| 拖动 #1 | 16.7 | 33.4 | 449.9 | **449.9** | 38/152 |
| 拖动 #2 | 16.7 | 33.4 | 66.6 | 66.6 | 38/113 |

CPU profile（拖动期间，采样 100µs）：

```
45.4% (idle)          35.1% (program)       1.6% react
 1.4% ye(react)        1.0% GC               0.9~0.5% flow-vendor
 0.7% elementFromPoint 0.7% querySelector
```

结论：**JS 不是瓶颈**（`(program)` = 渲染占 33~45%，idle 32~45%）。
真正吃掉帧预算的是**每帧重绘**：拖动选中卡片时与之相连的连线会进入 `is-linked`
并跑起三层 dashoffset 动画，而这些贝塞尔路径每一帧还要跟着节点重排 —— 一边重排一边重绘。

顺带纠正一个误判：静止画布上流光是**不跑**的（实测 216 个流光层里 0 个在跑，
`.canvas-edge-flow` 只在 `is-busy / is-linked / hover / selected` 时才挂动画）。
所以优化点精确落在「交互期间」。

trace 还显示首次拖动的大头是 `GPUTask 1118ms / Layerize 156ms`（headless 软渲染），
建图层 + 光栅 —— 对应「拖动期间给**所有**节点加 will-change」这一条。

## 二、改了什么

### 1. 吸附：从「被拽过去」改成「被吸过去」

`canvasLayout.easeAlignSnap(applied, target, eps, k)`：每帧只把修正量推进
`k=0.52`，差值 <0.5 屏幕像素时取齐（4 帧 ≈ 67ms 收敛）。

- 以前：指针刚跨进 enter 阈值（8 屏幕 px）的那一帧，卡片瞬间横移 8px → 「啪一下」。
- 现在：参考线画的是**目标**位置（solved 算的就是目标值），所以线先出现、卡片再滑进去。
- 松手时用 `snapResidualRef` 把没走完的那一点点补上，落点必须精确贴线。

### 2. 交互期暂停连线流光

拖卡片 / 平移 / 缩放期间，给 `body` 打 `data-canvas-interacting`，
CSS 用 `animation-play-state: paused` 停掉三层流光与终点火花。

★ 开关写在 **body 的属性**上而不是 React state：改 state 会在手势开始那一帧
触发整棵画布重渲染，恰好是手感最敏感的一刻；React 从不管理 body 属性，直接写 DOM
不会和任何一次 render 打架。

### 3. 只给真正在动的节点提合成层

`.canvas-flow.is-node-dragging .react-flow__node { will-change: transform }`
→ `.canvas-flow .react-flow__node.dragging`。
以前一屏 21 个节点就是 21 个图层，建层那一下正落在「刚按下鼠标」这一帧（首次拖动 450ms 的主因）。

### 4. 缩放按钮 / 重置 / Ctrl+0 以视口中心为锚 + 180ms 过渡

旧实现只改 `zoom`、不动 `x/y`，等于绕**画布左上角**缩放（`screen = world × zoom + {x,y}`），
连点几下内容全跑到右下角外面。现在反算 `x' = cx - (cx - x) · k`，
并用 `rf.setViewport(next, {duration: 180})` 过渡。

### 5. 每帧少做一半的事

- **对齐候选快照**：拖动过程中其它卡片不会动（本项目没有自动布局），
  所以一轮拖动只快照一次 `others`，每帧从 O(节点数) 降到 O(被拖数)。
  只在 `draggingRef` 为真时复用（键盘微移/程序化移动不走拖动，缓存会陈旧）。
- **编组外框去重**：先算出要写入的字符串，和上一帧的签名完全相同就一个字节都不写；
  DOM 映射按「组 id 列表 + 容器节点」缓存（该函数每帧被调用两次）。
- **光标提示**：rAF 合批（一帧最多算一次）+ 先用纯算术的矩形判定，
  只有真的落在框内才做 `elementFromPoint`（原来每次 pointermove 都做整树命中测试 + 逐个 getBoundingClientRect，
  pan 时 elementFromPoint 单独占 1.3% CPU）。
- **预热参考线节点池**：挂载时空跑一次 `updateAlignGuides([])` 把 8 个 div 建好，
  不再把建 DOM 算进首次拖动。

## 三、踩到的坑（会复现，记下来）

**`const` 声明顺序 → TDZ。** 我把「几何签名去重」那段插到了 `PAD` / `HEAD`
声明**之前**，而它们是 `const`。表现：`ReferenceError: Cannot access 'gt' before initialization`，
**只要项目里存在编组，加载即整页报错、卡片全部不渲染**。
定位手段：CDP `Runtime.exceptionThrown` 拿堆栈（列号是 0-based，且 bundle 的第 21 行才是超长行），
再按列号从 `dist/assets/index-*.js` 里把那段切出来看。

## 五、遗留

- headless 是软件光栅，`GPUTask` 占比被放大；真机（有 GPU）的绝对数会更好，
  但「减少每帧重绘」这个方向不变。
- 吸附缓动让卡片相对指针最多滞后一个修正量（≤8 屏幕像素，67ms 内收敛），
  这是「磁吸感」的代价；如果觉得粘手，把 `ALIGN_SNAP_EASE` 调到 0.7~1.0 即可（1 = 退回旧行为）。

## 六、补丁（同日 18:05）：点阵间距忽大忽小（版本 2026.11.02.13）

用户：「点阵背景 为什么缩放到 36% 反而点间距大了 到 42% 反而小了」。

### 根因：用离散档位去满足连续约束

`canvasBackgroundMetrics` 为了让屏幕间距不落在 [10,52]px 之外，用的是
「世界间距**翻倍 / 减半**」的离散档位：

```
36% → 24 × 0.36 = 8.64  太密 → 世界间距翻倍成 48 → 屏幕 17.28px
42% → 24 × 0.42 = 10.08 达标 → 不翻倍            → 屏幕 10.08px
```

跨过临界点的瞬间，屏幕间距会从「约 2×下限」直接掉回「1×下限」——**放大反而变密**。
这不是 36%/42% 这一处，而是整条曲线都是锯齿：

| zoom | 12% | 19% | 33% | 36% | 42% | 57% | 100% | 200% | 267% | 800% |
|---|---|---|---|---|---|---|---|---|---|---|
| 旧（翻倍档位） | 11.52 | 18.24 | 15.84 | 17.28 | 10.08 | 13.68 | 24 | 48 | **32.04** | 48 |
| 新（连续钳制） | 8 | 8 | 8 | 8.64 | 10.08 | 13.68 | 24 | 48 | 64 | 64 |

旧曲线在 19%→33%、36%→42%、200%→267% 等多处反向。

### 修法：改成连续钳制

先算屏幕值、钳到上下限、再换回世界坐标：

```ts
const pitchScreen = clamp(CANVAS_DOT_PITCH * z, 8, 64);
const gap = pitchScreen / z;          // 换回世界坐标
const size = clamp(CANVAS_DOT_SIZE / z, 0.2, 10);   // 屏幕恒 2px 直径
```

屏幕间距 = `clamp(24 × zoom, 8, 64)`，对 zoom **单调不减**，且不会再跳档。

下限取 **8**（而不是原来的 10）：让 33% ~ 267% 这段常用缩放落在完整等比区间里，
用户在常用区间缩放时能明确看到点阵跟着一起放大/缩小；只有全览到底（<33%）时
才固定在最密的一档，避免点连成灰膜和摩尔纹。

### 验证

- 单测 **483 passed**（+3）：
  - 全区间单调性遍历（zoom 0.12 → 8，步长 0.01，共 789 个采样点）
  - 36% 的间距 ≤ 42% 的间距（用户反馈的那个 case）
  - 相邻缩放之间不存在 2 倍跳变
  - 旧的「全览翻倍 / 放大减半」两条断言按新语义改写
- 端到端（隔离实例 8895，读 `--canvas-pitch` 计算值）：
  12%→8px、30%→8px、**36%→8.64px、43%→10.32px**、52%→12.48px、107%→25.68px、154%→36.96px，
  单调递增 ✓，console 0 报错

### 教训

**「用离散档位去满足一个连续约束」必然在某处反向。**
凡是「屏幕密度要落在某个区间」这类需求，都应该用 clamp（连续）而不是翻倍/减半（离散）。

## 一、虚线深浅不一：真因是「小数 DPR」，不是颜色

### 证据（用户截图，1770×947）

三条平行参考线，逐行统计蓝色像素的 RGB：

| 线 | 上一行亮度 | 下一行亮度 | 该线墨量 |
|---|---|---|---|
| 第一条 | B=77 | B=217 | 294 |
| 第二条 | B=143 | B=151 | 294 |
| 第三条 | B=207 | B=88 | 295 |

**三条线的总墨量几乎完全相等，但峰值的分配方式完全不同** —— 这是「同一条 1 像素宽的线落在不同设备像素相位上」的指纹，不是配色问题。

### 根因

第 27 轮修的是「对齐到整数 CSS 像素」。这在 DPR=2（200%）的屏上成立，但 Windows 最常见的 **125% / 150%** 缩放下 DPR 是小数（1.25 / 1.5）：

```
整数 CSS 位置 × 1.25 = 0, 1.25, 2.5, 3.75, 5.0 …
                        ↑只有 1/4 落在整数设备像素上
```

一个 1 CSS px 宽的窄矩形压在 1.25 上时，浏览器把它劈给相邻两行设备像素（0.75 + 0.5 或 1.0 + 0.25），**总墨量不变、峰值亮度差一倍** → 肉眼「有的线深、有的线浅」。

### 修法

`canvasLayout.ts` 新增三个纯函数：

- `alignGuideDeviceQuantum(dpr) = 1 / dpr` —— 吸附栅格按**物理像素**，不再按 CSS 像素；
- `alignGuideStrokeDevicePx(zoom, dpr)` —— 线宽取整到**整数个物理像素**（1px @ DPR1.25 → 1 个物理像素 = 0.8 CSS px）；
- `alignGuideDashDevicePx(dpr)` —— 虚线节奏同样取整到整数物理像素（4px @ DPR1.25 = 5 个物理像素）。

`CanvasView.updateAlignGuides` 里同时对齐两处：

1. **垂直方向的位置**（线的粗细落哪一行）；
2. **沿线方向的起点**（虚线的图案从元素原点开始铺，起点差半个物理像素 → 每一段虚线边缘都做覆盖率混合，整条线看起来「淡一档」）。

### 验证（DPR=1.25 的隔离实例，真实拖动）

```
guides [{"is-v","w":"0.8px","h":"852.8px"},
        {"is-h","w":"2051.6px","h":"0.8px"},
        {"is-h","w":"639.6px","h":"0.8px"},
        {"is-h","w":"639.6px","h":"0.8px"}]
```

截图像素统计：参考线所在行 **140~326 个像素全是纯色 `rgb(47,111,235)`**，相邻行没有任何混合色 —— 每条线恒为「1 个物理像素的纯色」。

## 二、点阵背景改成随缩放 / 平移

**旧实现**：`.canvas-background-pattern` 上的 CSS `background-image: radial-gradient(...)` + `background-size: 24px 24px`。
这里的 24px 是**屏幕像素**，所以缩放时点阵纹丝不动、平移时也不跟画布滚 —— 本质是一张贴死的壁纸。

**新实现**：改用 React Flow 的 `<Background>`（SVG pattern）。库内部已经是：

```
scaledGap = gap × zoom          // 间距随缩放
pattern.x = panX % scaledGap    // 跟着平移滚
```

新增 `canvasBackground.canvasBackgroundMetrics(zoom)`：

- 间距按屏幕落点 `[10, 52]` px 来**翻倍/减半**（19% 全览 → 96px 世界间距，否则 24×0.19 = 4.6 屏幕像素，点连成灰膜还出摩尔纹；800% → 6px）；
- 点径 `2 / zoom` 反向补偿，屏幕上恒为 ~2px（否则全览时圆点只有 0.4px，抗锯齿后直接消失）。

CSS 侧 `.canvas-background-pattern[data-bg='dots'|'lines'] { background-image: none }`，只留画布底色，避免两层底纹叠加。

**注**：本机单用户模式（`/api/preferences` 需要账号，本机模式返回 401）无法在隔离实例里把底纹偏好改成点阵，所以这一项没有截到 dots 实图；机制由库保证，间距/点径换算有 6 项单测覆盖。

## 三、连线流光：不再整屏同步，也不再「悬停瞬移」

1. **每条边一个固定相位**（`edgeFlowPhaseDelay(id)`：对 id 做稳定哈希 → `-0 ~ -3.2s` 的 `animation-delay`）。
   原来几十条线共用同一套 keyframes、同 3.2s、同相位 0，一闪全闪，远看像节拍器。
   负延迟顺带解决「每次 hover 彗星都从起点重新出发」——现在直接从周期中段接着流。
2. **去掉 hover / selected / busy 上的 `animation-duration` 覆盖**。
   CSS 动画进度 = `(已播时间 + |delay|) / duration`，中途改 duration 会让彗星**瞬移**到路径另一头。
   现在速度恒定，悬停只做「更亮、更粗、终点火花脉冲」。
3. 三层（焰尾/彗身/彗头）共用**同一个** delay，否则会散成「串珠」。

## 四、拖动「抬起」与丝滑度实测

- 拖动中节点光标 `default → grabbing`。
  ★ 类名坑：拖动中节点的 className 是
  `react-flow__node react-flow__node-media nopan selected selectable draggable dragging`，
  **没有** `react-flow__node-draggable`，照旧类名写选择器永远不命中（实测 computed 仍是 default）。
- 拖动中的卡片阴影加深（抬起感），松手 160ms 平滑落回。
  ★ 必须 `!important`：`theme-tokens.css:1545` 是 `box-shadow: var(--v-shadow-card) !important`，
  不写会被原样顶掉。
- 帧率实测（headless Chrome + software raster，1440×900 @ DPR1.25）：

  | 场景 | p50 | p90 | 备注 |
  |---|---|---|---|
  | 静止 | 16.7ms | 16.7ms | 基准 60fps |
  | 平移画布 | 16.7ms | 16.8ms | 偶发一次 200ms（raster） |
  | 拖动卡片 | 16.7ms | 16.7ms | 首次拖动偶发 100~780ms（一次性） |

  CPU 采样：拖动/平移期间主线程 **88~96% idle**，JS 侧没有热点（最大项是 React Flow 自己的 store 更新 1.1%）。
  结论：卡顿不在我们的每帧逻辑里，而在合成/光栅（headless 是软件渲染）。
  唯一可复现的「第一次拖动卡一下」= 首次建立图层 + 首次创建参考线 DOM 池。

## 六、补丁（同日 16:00）：参考线改「屏幕像素直出」+ 相邻线合并

用户第三次反馈「辅助虚线还是会出现明显深浅」，附 1119×925 截图。

### 为什么上一版没解决

从他的截图能反推出环境是 **DPR≈1**（截图与 CSS 1:1）：
- 虚线周期实测 8 图像像素 = 设计值 8 CSS px；
- 点阵间距实测 15.4 = 24 × 0.63（当前缩放）。

DPR=1 时「设备像素」和「CSS 像素」本来就是一回事，第 29 轮那套 `1/DPR` 吸附在他的机器上是**空操作**——所以「还是」。

### 真正看到的两个问题（像素实测）

1. 一条竖线只占 **1 列**（纯色，正常）；另一条占 **2 列**（x=830 亮 157 行、x=831 亮 118 行，颜色相同）。
   → 不是「深浅」，是**两条线的目标边只差 1 个像素，吸附后落到了相邻两列**：
   视觉上是一条 2px 粗线，而且两条线的虚线相位不同、互相穿插，看起来又粗又断。
2. 虚线节拍实测是 **3 实 5 空**（设计 4/4）。因为线画在画布坐标系里、被 transform 缩放，
   每段两端各被抗锯齿吃掉约 0.5px。

### 修法

**A. 相邻线合并**（`canvasLayout.mergeAdjacentAlignGuides`）
同轴、间距 ≤1 个物理像素的线合并成一条，区间取并集，位置保留先出现的那条（已在栅格上）。

**B. 参考线层移出画布变换**（结构性修复）
以前整层挂在 `ViewportPortal` 里，随 `translate(x,y) scale(z)` 一起缩放，线宽/虚线节奏只能靠 `1/zoom` 反算 —— 永远在跟 transform 的亚像素相位打架。
现在 `.canvas-align-guides` 是画布容器上的屏幕坐标覆盖层：

```
left = world.x * zoom + panX      // 单位就是 CSS px
top  = world.y * zoom + panY
width/height = 1 个物理像素（alignGuideStrokeDevicePx）
dash = 4 个物理像素（alignGuideDashDevicePx）
```

没有中间缩放，也就不存在相位问题。层级：`z-index: 4`（与 `.react-flow__renderer` 同级、DOM 更晚 → 压在卡片和连线之上），低于 RF 面板的 5，不会盖住小地图/工具栏。

### 实测（隔离实例，50% 缩放）

| 环境 | DOM 写入 | 竖线列数 | 虚线节拍 |
|---|---|---|---|
| DPR 1 | `left=370px w=1px dash=4px` | **1 列**（255 行），左右列 1 / 8 行（噪声） | **4 实 4 空** |
| DPR 1.25 | `left=370.4px w=0.8px dash=4px` | **1 列**（238 行纯 `rgb(47,111,235)`） | 5 实 5 空（= 4/4 CSS） |
